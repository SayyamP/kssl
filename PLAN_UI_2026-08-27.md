## 1. Profile tab (new) — Competitive rail, below Overview

### What is asked for vs what exists

| requested section | backing data | verdict |
|---|---|---|
| company name / identity | `name, sector, hq, site, threat` | **build** (`hq` is null on most) |
| products | `products[]` (names) + `matchups` (specs) | **build** |
| product detail | `matchups[].reason/bf/comp/cat` | **build**, 11 companies only |
| status | `threat` + `threatNote` | **build** |
| news | signal cards filtered on `company` | **build** — but only 5 of 29 have any |
| company related news | same as above | same |
| tech | `innovations[].driver` matches company | **build** |
| facilities | — | **NO DATA.** `geoData` is *product presence by country*, not sites |
| leadership | — | **NO DATA.** No field, nothing in the corpus |
| sales data | — | **NO DATA.** `value` is null on all 89 tenders |
| timeline / upcoming | — | **NO DATA.** No dated event series per company |
| development | partial — `innovations[].mat === "dev"` | **build as "in development"**, thin |

Four of the twelve requested sections have **zero** backing rows. They will not be
rendered as empty boxes and they will not be filled with a plausible guess — the standing
rule is that "not measured" must not look like zero. They get one honest strip at the
bottom of the profile naming what is not collected, so the gap is visible rather than
silent.

### Files

- `frontend/src/pages/competitive/Profile.jsx` — new
- `frontend/src/lib/profile.js` — new; pure, builds one profile object per company id
- `frontend/src/styles/profile.css` — new
- `state/AppState.jsx` — add `{ view: "profile", label: "Company Profile", ix: "01" }`
  to `RAIL.competitive`, renumber `ix` on the rows below it
- `components/layout/Layout.jsx` — `case "profile": return <Profile />`
- `lib/overview.js` — `counts.profile` = number of rivals; a `viewMetaFor` entry

### Shape

Two columns. Left: a searchable company list (29 rivals, `compOrder` for ordering, a
threat dot and a "has data" density bar). Right: the selected company's sections, each
one rendered **only if it has rows**:

```
identity      name · sector · HQ · site link · threat pill
assessment    c.assess (already HTML)
products      products[] as chips; each chip that appears in a matchup opens its spec rows
spec detail   matchups for this company: category, its product vs the client's, reason
development   innovations rows where driver === company and mat === 'dev'
news          signal cards where card.company === name — click opens the same DetailPanel
partnerships  c.partners[] — label, country, rel type, note, source
presence      geoData[cid] by country — name, stage, qty, since
patents       PATENTS.byAssignee[company]
sources       companySources[cid] / c.srcs
not collected leadership · facilities · sales · timeline  (one line, greyed, explicit)
```

Reuses `AppState.setScope` so Ask Mallory is scoped to the selected company, exactly as
Positioning and Partnerships already do.

### Risk

`updates` is a list on some companies and an HTML string on others — read it through one
guarded helper, never `.length` directly. This is the same class of bug as the two blank
dashboard pages (a key that exists but is the wrong shape passes every presence check).

## 6. Market pillar — rebuild as the JSW tender overview

Target: `187.127.134.12:8096/#p=market&v=overview`. Its component and CSS were read out
of the deployed bundle; the class vocabulary is `ov-report`, `ovtabs`/`ovtab-*`,
`ovc`/`ovc-grid`, `ovp-*` (donut), `ovb-*` (bars), `ovt-*` (table) — 52 CSS rules, all on

`Overview · Tender Pipeline` — `awarded-tenders` and `closed-tenders` fold into the

## 7. Every pillar's detail panel — keep only At a glance + What happened

`components/detailPanel/DetailPanel.jsx`:

- delete the **"Why it matters to {client}"** section (`detail.why`)
- delete the **"Full-spectrum read"** section (`detail.lens`) — this is the evidence list
- keep At a glance, What happened, the tender match block and Source

One panel serves all three pillars, so this is one edit for all of them.

`detail.why` is still the text `SignalCard` renders as `.sowhat` under each row, so the
"so what" is not lost from the screen — only from the drawer.

### Adding more to "At a glance"

`facts` is hardcoded to exactly four rows in `pipeline/serving_fill.py:646` — Company,
Category, Date, Primary lens — on all 14 details.

The extra rows the articles actually contain (contract value, quantity, counterparty,
programme name, country) exist **only inside the free-text `ev_quote` of
`extracted.proposition`**. Deriving them with regexes in the browser would be
manufacturing structure out of prose, which is the exact failure this codebase has been
burned by before.

The honest route is one backend change: `serving_fill.py` already reads
`(subject, predicate, object, modality, ev_quote)` and the derived layer already carries
typed `span_value` / `prop_arg` rows. Emit facts from the typed spans, each one carrying
its quote, and drop any that no span backs.

Proposed additional rows, each gated on a real span:

```
Counterparty   object of an award/order/contract predicate, when it is an Org span
Value          Money span in this document, with the quote
Quantity       Quantity span bound to a product argument
Programme      Product span in the title or in the first proposition
Country        Location span
Source         host of url  (currently only in the Source section)
Stance         threat / watch / favourable (currently only the header pill)
```

`Source` and `Stance` need **no** pipeline work — both are already on the card. They ship
in this pass. The other five ship with the `serving_fill.py` change and a re-run.
